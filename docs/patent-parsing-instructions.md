# 특허 문서 파싱 지침

특허 원문(PDF, HTML, 텍스트 등)을 받아 파이프라인이 요구하는 JSON 파일 3종으로 변환한다.

---

## 산출물 구조

출원번호 하나당 아래 폴더 구조로 저장한다.

```
data/input/{출원번호}/
├── patent.json
├── office_action.json
└── prior_arts/
    ├── 인용발명1.json
    ├── 인용발명2.json
    └── ...
```

---

## 1. patent.json — 출원 명세서

파이프라인이 실제로 읽는 필드만 기재한다. 나머지는 있어도 무시된다.

```json
{
  "발명의명칭": "...",
  "요약": "...",
  "특허청구범위": {
    "청구항1": "전체 청구항 1 원문 (한 문자열)",
    "청구항2": "...",
    "청구항3": "..."
  },
  "명세서": {
    "임의섹션명": [
      { "단락번호": "0001", "내용": "단락 내용" },
      { "단락번호": "0002", "내용": "단락 내용" }
    ],
    "다른섹션": [
      { "단락번호": "0010", "내용": "..." }
    ]
  }
}
```

**규칙:**
- `특허청구범위` 키는 반드시 `청구항1`, `청구항2` ... 형식 (숫자 붙임)
- `명세서` 내부 섹션 이름은 자유 — 단락 배열만 포함하면 됨
- `단락번호`는 원문 `[숫자]` 표기에서 추출, 4자리 0-패딩 권장 (`"0001"`)
- 단락이 없는 섹션(예: 단순 텍스트)은 배열 대신 문자열로 넣어도 파싱에서 무시됨 (빠뜨려도 무방)

---

## 2. office_action.json — 의견제출통지서 (OA)

파이프라인이 LLM에 raw dict 전체를 넘기므로 **원문 구조를 최대한 보존**한다.
단, `구체적인거절이유` 내부의 구성비교표는 아래 구조를 반드시 지켜야 심사관 판단이 자동 추출된다.

```json
{
  "문서정보": { ... },
  "출원정보": {
    "출원번호": "10-XXXX-XXXXXXX"
  },
  "심사결과": {
    "거절이유목록": [
      {
        "거절이유가있는부분": "청구항 제1항, 제4항 내지 제7항",
        "관련법조항": "특허법 제29조제2항"
      }
    ]
  },
  "구체적인거절이유": {
    "거절이유1": {
      "법조항": "특허법 제29조제2항",
      "청구항별거절이유": {
        "제1항": {
          "진보성비교": {
            "구성비교표": [
              {
                "구성": "구성1",
                "이출원제1항발명": "출원 청구항의 해당 구성 텍스트",
                "인용발명1": "인용발명1의 대응 구성 텍스트",
                "비고": "동일"
              },
              {
                "구성": "구성2",
                "이출원제1항발명": "...",
                "인용발명1": "...",
                "비고": "차이"
              }
            ],
            "심사관판단": "심사관 판단 텍스트 전문",
            "결론": "결론 텍스트"
          }
        }
      }
    }
  }
}
```

**`비고` 허용값:** `"동일"` / `"유사"` / `"차이"` — 이 세 값 외에는 모두 `"차이"`로 처리됨

**구성비교표가 없는 경우** (신규성·기재불비만 있는 OA 등): `구체적인거절이유` 안에 `청구항별거절이유`나 `구성비교표`를 넣지 않아도 됨. LLM이 전체 raw dict에서 거절이유를 파싱하므로 원문 텍스트가 포함되면 충분하다.

## 3. prior_arts/인용발명N.json — 인용발명

파일명은 반드시 `인용발명1.json`, `인용발명2.json` ... 순서 그대로.

```json
{
  "발명의명칭": "...",
  "요약": "...",
  "특허정보": {
    "출원번호": "10-XXXX-XXXXXXX",
    "공개번호": "10-XXXX-XXXXXXX"
  },
  "특허청구범위": {
    "청구항1": "청구항 전문",
    "청구항2": "..."
  },
  "명세서": {
    "실시예": [
      { "단락번호": "0020", "내용": "..." }
    ]
  }
}
```

**규칙:**
- `patent.json`과 동일한 구조
- `특허정보.출원번호`와 `특허정보.공개번호`는 반드시 포함 (파이프라인이 인용발명 식별에 사용)
- 파일이 여러 개면 OA에 언급된 순서대로 번호 부여
- **인용발명이 일본어 특허인 경우** — JSON의 키 이름(`특허청구범위`, `청구항1`, `발명의명칭`, `명세서` 등)은 반드시 한국어를 유지하고, 값(청구항 텍스트, 요약 등 내용)은 일본어 원문 그대로 넣는다.

---

## 파싱 시 주의사항

1. **원문에 없는 내용을 절대 추가하지 않는다.** 원문에 존재하는 텍스트만 그대로 옮긴다. 요약, 보완, 추론한 내용을 JSON에 삽입하는 것은 금지.
원문에 있는거 다 출력했으면 반드시 마무리 지어야함

2. **청구항 원문은 분리하지 않는다.** 하나의 청구항 전체가 하나의 문자열이어야 한다. 구성요소별로 쪼개지 말 것.

3. **구성비교표의 `이출원제1항발명` 키** — OA 원문에서 열 이름이 다르더라도 반드시 이 키 이름을 사용한다.

4. 여기는 로컬환경이 아니니까 디렉토리 위치는 생각하지 않아도 됨
